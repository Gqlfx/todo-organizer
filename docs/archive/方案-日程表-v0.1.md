## 一、一句话定义

把随口的一句话，变成今天真能做完的时间块。

输入：「周四前把方案给老板，还有买猫粮、约牙医」
输出：Today 视图里三个时间块，按"重要 × 紧急"和可用时间排好；装不下就问你砍哪个。

## 二、三个必须钉死的决定（其余都是细节）

### 决定 1：四象限是视图，不是引擎

- 只做四象限 = 一个高级便签。用户第 3 天就会想"我分类完了，还是不知道什么时候做"。
- 数据只有一份 `Task`，四象限 / 时间轴 / 收件箱是同一份数据的三种投影。
- 架构上：一张表 + 三个 `view`。任何视图上的修改都写回同一张表。
- 这样"拖到 Q1"和"拖到 9:00"是同一个动作的两个入口，不会打架。

### 决定 2：AI 只负责"抽取"和"建议"，排布交给确定性算法

- LLM 擅长：把"下周三下午三点前"变成 `due_at`，从语气里猜重要程度。
- LLM 不擅长：在 6 小时空档里塞 9 件事还不违反约束，而且每次结果都不一样。
- 所以：LLM 只输出结构化 JSON + 建议分值；排布用贪心 + 约束校验（20 行代码）。
- 好处：可解释（"排在 9 点，因为你标了 Q1 且上午有 90 分钟空档"）、可复现、便宜、不幻觉。
- 反模式：让 LLM 直接吐"你的日程应该是这样"，用户改一次它就废了。

### 决定 3：用"今日容量"逼出取舍

- 没有容量约束的自动排程 = 愿望清单。人一天真正的深度时间大概 3–4 小时。
- 装不下时不是往下堆，而是弹一个必须回答的问题：
  **"今天只剩 5.5 小时，这 3 件里哪件顺延？"**
- 这一个交互决定产品是"又一个待办清单"还是"真的帮你做决定"。

## 三、用户与三个高频场景

自用优先：先服务你自己两周，再谈产品化。

| 场景 | 触发 | 期望 | 设计要点 |
|---|---|---|---|
| S1 晨间倾倒 | 早上坐下 | 30 秒倒完脑子里 8 件事 | 单输入框，多行 = 多条，回车即提交，不弹窗 |
| S2 白天插入 | 开会时冒出一件事 | 一句话塞进去，知道它插在哪 | 全局快捷键 + 悬浮输入；提交后回"已排到 15:30"或"今天满了" |
| S3 晚间崩塌 | 一天没做完 | 一键把剩下的挪到明天 | "重排今天剩余" + "顺延到明天"，原始 deadline 不能丢 |

S3 的优先级不低于 S1：计划一定会崩，价值在崩了之后能不能 30 秒恢复。

## 四、主流程（六段管道）

| 阶段 | 输入 | 输出 | 失败怎么办 |
|---|---|---|---|
| 1 捕获 | 任意文本 | 原始字符串 | 空 / 纯表情 → 静默丢弃 |
| 2 解析 | 原始串 + 当前时间 + 时区 + 用户习惯 | Task 草稿（JSON） | 时间抽不出 → 进"待澄清"收件箱，不阻塞 |
| 3 判定 | 草稿 + 历史纠正记录 | 建议重要度 / 紧急度 | 不确定 → 默认 Q2，等用户改 |
| 4 排布 | Task 池 + 今日空闲窗 + 精力曲线 | 时间块序列 | 装不下 → 取舍弹窗 |
| 5 执行 | 时间块 | 完成 / 跳过 / 顺延 | 超时未完成 → 问一句"还在做吗" |
| 6 复盘 | 一周记录 | 估时偏差、象限分布 | 数据不足 → 只显示，不评判 |

**第 2 段失败绝不能变成报错弹窗。** 解析不出来就存原文让用户手工补，绝不打断输入流。

## 五、数据模型（一张表就够）

```
Task
  id, title, raw_input, status(todo/doing/done/deferred/dropped)
  -- 时间
  due_at, start_at, duration_min, is_fixed(硬日程/软待办), rrule
  -- 判定（双轨：AI 建议 vs 用户确认）
  suggested_importance(1-5), importance(1-5|null), urgency_manual(bool)
  quadrant            -- 派生字段，不手工维护
  -- 排布
  plan_date, slot_start, slot_end, is_locked(钉住，不参与重排)
  -- 溯源与学习
  source(manual/ai), parse_confidence, corrections(jsonb)
  -- 关系
  project_id, tags[], depends_on[]
```

派生规则：

```
urgent    = due_at 距今 ≤ 72h  或  urgency_manual
important = importance ≥ 4     （用户确认值优先，否则用 suggested_importance）
quadrant  = important ? (urgent ? Q1 : Q2) : (urgent ? Q3 : Q4)
```

`corrections` 是护城河：每次用户改 AI 的重要性或时长，存一条
`{raw_input, ai_said, user_said}`。下次同类输入作为 few-shot 注入，20 条就能明显变准。

## 六、排布算法（真正的核心，也最容易被跳过）

**输入**
- 今日可用窗：从日程里扣掉硬日程、会议、通勤，得到若干空闲段（如 09:20–11:30、14:00–16:00）
- 待排池：`plan_date ≤ 今天` 且未锁定
- 精力曲线：默认上午深度、午后浅层，可手动调

**硬约束（必须满足）**
1. 硬日程不动
2. 时间块不落在过去
3. deadline 前必须排完（排不完 → 进取舍弹窗）
4. 单块 ≤ 90 分钟，超长任务自动拆两段
5. 块间留 10 分钟缓冲

**软目标（加权打分，贪心填充）**

```
score(task, slot) =
    3.0 * 象限权重(Q1=1.0, Q2=0.8, Q3=0.4, Q4=0.1)
  + 2.0 * deadline 紧迫度（归一化）
  + 1.5 * 精力匹配（深度任务 × 高能时段）
  + 1.0 * 用户手动排序偏好
  - 1.0 * 估时偏差惩罚（历史实际/估算 > 1.5 则降权）
```

**算法**：按分数降序取任务，找第一个装得下的 slot（best-fit）；装不下进 overflow → 触发取舍。
复杂度 O(n·m)，几十个任务毫秒级。

不要一上来上 CP-SAT / OR-Tools：约束还会变，先跑通再加。

## 七、AI 管道与输出契约

**解析用 JSON Schema 强约束**（function calling）：

```
{ items: [{
    title, start_at?, due_at?, duration_min?,
    importance_hint: 1-5, energy: "deep"|"light",
    confidence: 0-1, needs_clarify: bool
}] }
```

Prompt 五个易踩的坑：
1. 必须注入当前时间、时区、星期几（"下周三"没有这个必错）
2. 明确"没提到时间就不要编"，宁可为 null
3. 一次输入多件事要拆条（顿号 / 句号 / 换行）
4. 相对时间归一化表："明天早上"→ 次日 08:00 起 60min；"月底前"→ 当月最后一天 18:00
5. 只输出合法 JSON，不要解释文字

**澄清策略：最多问 1 个问题，且可以先存后问。**
宁可存一个不完整的任务，也不要在输入流里开对话框——这条直接决定"顺手"还是"烦人"。

**每晚清洗（定时任务）**
- 重复标题合并（编辑距离 + 同 due 窗口）
- 超 14 天未动的 Q4 → 建议归档
- 估时异常（实际/估算 > 2）→ 下次自动调估时

## 八、技术选型

| 层 | 选型 | 理由 | 什么时候换 |
|---|---|---|---|
| 前端 | Next.js 15 + TS + Tailwind + shadcn/ui | 一套代码 Web + PWA，生态熟 | 要上架 App 时套 Capacitor |
| 拖拽 | dnd-kit | 时间轴和象限都能用，无需重度改造 | 不换 |
| 本地 | Dexie(IndexedDB) 本地优先 | 秒开、断网可用、隐私好 | 多端实时协作时加 CRDT |
| 后端 | Supabase（Postgres + RLS + Auth） | 起步最快，行级权限省事 | 数据量/合规要求高时迁自建 |
| AI 网关 | 服务端 `/api/parse` 代理 | key 不下发前端，可加缓存与限流 | 不换 |
| 模型 | 国产小模型（DeepSeek / 通义）+ JSON 模式 | 中文时间表达好、便宜 | 解析不稳再上大模型 |
| 提醒 | 先站内 + 邮件；后期 Web Push / 微信服务号 | 微信触达最有效 | — |
| 部署 | 国内轻量服务器 + 备案（自用可先 localhost） | Vercel 国内访问不稳 | — |

成本量级：一次解析 300–500 tokens，一天 20 条，国产小模型几分钱/月，可忽略。

## 九、版本路线（狠砍，别贪）

### V0.1 自用可用（7–10 天）
1. 单输入框，支持多行 = 多条
2. AI 解析成卡片，可改：时间 / 时长 / 重要性
3. Today 视图：时间轴 + 四象限两个 Tab（同一份数据）
4. 拖拽调顺序、拖拽改时间块
5. 完成 / 顺延（一键挪明天，保留 deadline）
6. "重排今天"按钮

### V0.2 好用（+2 周）
周视图 · 重复任务 · 估时校准 · 周复盘（完成率 / 象限分布 / 估时偏差）· 每晚清洗

### V0.3 能给别人用
账号与多端同步 · 推送提醒 · 分享日程 · 日/周/项目模板

### 明确不做（第一版）
团队协作 · 甘特图 · 双向同步 Google/Outlook · 语音输入 · 聊天式 AI 助手 · 主题皮肤

> 尤其"聊天式助手"：日程软件的用户不想聊天，想丢一句话就走。做 chat 会把最珍贵的"顺手"变成"对话成本"。

## 十、风险与我反对的做法

1. **最大的风险不是技术，是"分类完就没人看"。** 四象限只解决"想清楚"，不解决"什么时候做"。V0.1 必须带时间轴，否则验证不了价值。
2. **AI 判重要性必然不准**（它不知道你的目标）。必须"建议 + 一键纠正 + 记住纠正"，否则用户三次之后就不看建议了。
3. **免费输入会导致任务爆炸。** 一句话能塞 10 件，全标 Q1。必须有容量约束和取舍弹窗，否则产品变焦虑放大器。
4. **自动排程的黑箱感。** 每块要能点开看"为什么排在这"（一句人话），否则不信任、一改就全乱。
5. **不要做"满分计划"。** 计划一定会崩，价值在崩后能否 30 秒恢复。

**竞品参照（差异化在哪）**

| 竞品 | 它已经有的 | 我们补什么 |
|---|---|---|
| 滴答清单 | 四象限视图现成 | 自动排布 + 容量取舍 |
| Sunsama | 每日仪式 + 时间块最接近 | 中文一句话输入、便宜 |
