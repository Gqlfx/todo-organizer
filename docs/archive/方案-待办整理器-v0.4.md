## 一、定位：它只解决三件事

| 你的说法 | 本质问题 | 对应能力 |
|---|---|---|
| "懒，想随便输入就自动整理好" | 捕获成本高 | 一个框、多行、不弹窗 |
| "需要全看一遍才能做时间安排" | 整理成本高 | AI 定序，零操作 |
| "想不起来、还怕遗漏" | 不确定有没有漏 | 打开即见 + 显式计数 |

**明确不做**：不管几点上课、不做周课表、不做时间轴网格、不做多端同步。

## 二、可用时间：不是常数，是七个估计值

### 2.1 为什么一个数字不行

"每天可用 240 分钟"错在四个地方：

- 周二满课，晚上可能只有 1 小时
- 周六没课，但也没人真想干 8 小时
- 考试周和平时是两个世界
- 最糟的是：系统会在满课那天给你排 4 小时的事，然后你**每天都完不成**，三天后就不信它了

### 2.2 模型：三层叠加

```
day_capacity = { 周一:180, 周二:120, 周三:180, 周四:120,
                 周五:240, 周六:480, 周日:480 }        -- 周模板，7 个值

override     = { "2026-11-20": 60 }                    -- 单日覆盖：考试、出游

可用(某天)   = override[该天] ?? day_capacity[星期几]
```

三层各管一件事：

| 层 | 解决什么 | 谁定 |
|---|---|---|
| 周模板（7 个值） | 规律性的差异 | 你，30 秒填完 |
| 单日覆盖 | 例外 | 你，点一下 |
| 系统建议 | 估计偏差 | **系统提议，你确认** |

第三层最重要：连续三天完成率低于 60% → 提示"要不要把周二从 3 小时调到 2 小时？"，**你点确认才改**。

不自动改。因为一个会自己改参数的排程器，和黑箱没区别——这跟"时间三种来源"是同一条原则：**系统可以建议，不能替你决定。**

### 2.3 填 7 个数字，其实就是把课表降维了

课表的价值有两块：

- **每节课是什么** → 你要查，已有软件负责
- **每天还剩多少空** → 只有这个系统需要

前者你不需要第二份，后者 7 个数字就说完了。**丢掉 15 门课的细节，只保留它们的结果。**

这也是为什么不做日历网格：网格提供**位置感**，你需要的是**容量感**。前者对"约人开会"有用，后者对"别把自己排爆"有用。你的场景里，后者远多于前者。

### 2.4 填写交互（30 秒，这是"懒"的硬要求）

不要给 7 个输入框。给四个预设按钮：

```
[紧张 2h]  [正常 4h]  [宽裕 6h]  [全天 10h]
        ↓ 一键套用到工作日
     再单独调周六、周日
```

填完立刻能在队列里看到效果，才叫"30 秒"。

## 三、长期视图：14 天负载条（V0.1.1）

队列只回答"今天"。但你会想问"下周会不会爆"。

**不做日历网格，做一根负载条：**

```
11/16 ▁▁  11/17 ▃▃  11/18 ▅▅  11/19 ██  11/20 ██▁
      周六      周日      周一      周二      周三
```

- 横向 14 天，每天一根柱
- 柱高 = 当天已排时长 ÷ 当天可用时长
- 超过 100% 标红（这天必爆），空白为灰
- 点某天 → 跳回那天的队列

它回答的是**密度**，不是位置。你要防的是爆炸，不是错约会议。

**V0.1 不做，也不留空入口**（点了是空的比没有更糟），V0.1.1 加一个 Tab。

## 四、时间的三种来源

| 来源 | 谁定的 | 视觉 | 数据 |
|---|---|---|---|
| **固定占用** | 外部世界（课、会、约） | 整行深色实心块 | `is_fixed = true` |
| **你定的** | 你 | 实线卡片 + "已锁定" | `slot_source = "user"`, `is_locked = true` |
| **系统推荐** | AI | 虚线卡片 + "系统推荐" + 理由 | `slot_source = "ai"` |

行为规则：

- **只有"系统推荐"会在重排时变动**
- 你一拖，立刻变"你定的"并锁定，之后永远不动
- 点锁可解除，退回"系统推荐"
- "你定的"不显示理由；"系统推荐"**必须**显示一句 ≤20 字的理由

**信任靠边界建立。** 分不清"我定的"和"机器猜的"，两个都不信。

## 五、防遗漏：三处，缺一不可

1. **顶部计数**：`今天 8 件 · 已排 3 件`
2. **队列底部**：`还有 5 件没排上 · 展开`
3. **全部清单**：纯列表，按到期/创建排，不进任何时间结构

①是数量感，②是"今天做不完"的诚实，③是"我没漏记"的确认。
**焦虑来自不确定，确定感来自可见。**

## 六、队列结构

```
周二           今天 8 件 · 已排 3 件      可用 2 小时
─────────────────────────────────────────
▎14:00–15:40  电路实验        实验楼 B    ← 固定占用

  · · · 15:40 之后 · 可用 1.5 小时 · · ·

  方案给老板                 90 分钟        ← 系统推荐（虚线）
  推荐 16:00–17:30 · 周四到期，还差两轮修改

  回邮件                     25 分钟        ← 你定的（实线 + 已锁定）
  17:40–18:05

  ─ ─ ─ 今天到此为止 ─ ─ ─

  写周报                     40 分钟        ← 线下，褪色
  明天

  还有 5 件没排上 · 展开
```

四种元素：固定行、推荐卡、手定卡、尽力线。**没有第五种。**

### 为什么没有"确认"按钮

AI 排完不弹窗、不让你点"确定"，直接进队列。三条理由：

1. **审核会毁掉唯一不能毁的东西——输入流。** 全部前提是"随便输入就走"，中间插一个确认弹窗，等于把 10 秒变成 30 秒，而 30 秒足够让你打开备忘录。
2. **三天后你会盲点确定。** 这是所有审核弹窗的宿命：前两次认真看，之后变成肌肉记忆。那时的确认不是把关，是仪式，还会制造"我核对过了"的虚假安全感——比不确认更糟。
3. **真正的审核时刻是"打开看今天"，不是"提交后那一秒"。** 早上扫一眼队列，立刻能看出哪条不对；那时改的成本最低，因为你已经理解了今天的处境（几点有课、还剩多少时间）。提交那一刻你没有这个上下文，只有"快点弄完"。

**但有一处必须确认：解析，不是排序。**

| 错误类型 | 可见性 | 处理 |
|---|---|---|
| 解析错（"周四"听成"周五"） | **低**，事后很难发现 | **前置展示**：卡片直接显示解析结果，时间可点改 |
| 排序错（该第 3 的排到第 7） | **高**，一眼就看出 | **后置纠正**：拖一下就改，不弹窗 |

判据不是"错误多严重"，是"**错误多容易被发现**"。不可见的错要前置，可见的错后置。

**撤销比确认重要。** 确认的成本每次都付，撤销的成本只在错的时候付。所以：拖拽即时生效、不弹"已保存"、提供一步撤销。

**唯一的例外**：一次粘 8 条以上时，给一个轻量清单——"已拆成 7 条，其中 1 条没看懂时间"，逐条可改。这是**确认理解**，不是确认顺序。

## 七、AI 分档，代码定序（本轮核心修正）

### 7.1 为什么不用"AI 全量排序"

- **幻觉**：让模型吐 30 条有序列表，它可能漏项、重项、编出不存在的 id
- **抖动**：每次调用结果不同，用户看到的是"每天换一张表"
- **成本**：每次都要传全部任务、输出全量有序列表
- **标度**：模型对"重要"没有稳定刻度，跨调用不可比

### 7.2 为什么不用"权重公式"

- 系数是拍脑袋定的，换个人、换个阶段就失效
- 用户手打的 1–5 星，在不同时期也不是同一把尺子

### 7.3 第三条路：档位

AI 只回答一个问题——**这条属于哪一档**。四选一：

```
now   现在做（今天必须开始，且时间上还来得及）
today 今天做（今天之内做完就行）
week  本周做（有截止，但不急在今天）
later 以后（没有明确截止，或明显不急）
```

输出 `{id, bucket, reason}`，一条几十个 token。

**reason 不能自由发挥。** 模型给的理由不是它的推理过程，而是事后生成的一段合理文本，
最容易掺进它根本不知道的细节。所以：

- **允许引用**：任务原文、截止时间、估时、是否逾期、被顺延过几次
- **禁止编造**：进度（"还差两轮修改"）、难度、谁在等这件事
- **更稳的做法**：reason 由代码拼装（`周四到期 · 90 分钟 · 已顺延 2 次`），
  AI 只负责给 bucket。理由里每一个字都必须是可核对的事实。

剩下全交给代码：

```
顺序 = 按档位分组(now > today > week > later)
     → 组内按 (due_at 升序, est_min 升序)      ← 短的先做，快速清空
     → 逐空档 first-fit 装填
     → 撞容量画"今天到此为止"
```

### 7.4 为什么这样更好

| 问题 | 全量排序 | 分档 |
|---|---|---|
| 幻觉 | 30 条都可能错位 | 至多偏一档 |
| 抖动 | 每次全表重排 | 只改新增那条，旧的不动 |
| 成本 | 每次 3–5k 输入 + 1k 输出 | 每次约 200 输入 + 10 输出 |
| 标度 | 跨调用不可比 | 档位是绝对标签，没有标度问题 |
| 错误代价 | 差 5 位立刻可见 | 错到相邻档几乎无感 |

**最关键的是"增量"**：新任务进来只问一句"这条放哪档"，已有顺序完全不动。
这从根上解决了人格漂移——大多数调用根本不碰旧数据。

### 7.5 代码侧四道闸（保留）

1. **合法性**：id 必须来自输入集，编造的丢弃，漏掉的按 `due_at` 补
2. **容量**：累加 `est_min`，撞到当天可用时长画"今天到此为止"
3. **硬约束**：固定行按时间插位；`due_at` 已过今天的强制置顶标红
4. **稳定化**：档位没变的任务，位置不变（不必再比 rank）

### 7.6 触发与降级

触发：新任务（**增量分档**）/ 用户拖拽（改档 + 锁定）/ 跨天 / 点"重排"（全量重分档）。

降级三层：超时 8s 重试 → 读上次档位快照 → 打星和拖拽永远可用。
**不写任何算法重排逻辑。**

## 十二、风险

1. **可用时间设太高 → 每天欠债 → 三天后弃用**。
   **宁可低估，别高估**：从"紧张 2h"起步，一周后往上调。低估只是排得少，高估是天天失败。
2. **排序人格漂移** → 四道闸第 4 道，别省。
3. **AI 让 Q1 挤掉 Q2** → "Q2 每天保底一位"写成 `prefs` 硬规则，代码执行。
4. **手机端不顺手就弃用** → 指标：解锁到提交 ≤ 10 秒。
5. **数据只在一台手机上** → 导出 JSON 是唯一保险。
6. **工期膨胀** → 任何新想法进 V0.1.1。
